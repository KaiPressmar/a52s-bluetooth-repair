# Galaxy A52s 5G Bluetooth call research

Research date: 15 October 2026. Repository baseline: `5f3a77d`. This analysis covers the existing Android app, public firsthand reports, Android documentation, and AOSP implementation references. It is the evidence base for the [refactoring plan](REFACTORING_PLAN.md) and [community plan](COMMUNITY_PLAN.md).

## Main conclusion

A bounded, automatic Telecom route recovery is a credible workaround for some Galaxy A52s 5G call failures. Its effectiveness against the recurring Samsung firmware failure still needs controlled tests on affected hardware. A normal installed app cannot guarantee recovery from every Bluetooth or vendor audio failure without a restart or privileged system help.

The product goal should remain: **after initial setup, supported failures recover during ordinary calls without opening the app, tapping a repair button, changing settings, or restarting the phone**. A failed recovery must remain a failed result in the evidence, rather than becoming a manual troubleshooting step counted as success.

The existing code already uses the right general control surface for cellular calls: Telecom. The highest priorities are proving call access on stock Samsung firmware, directing actions to the intended endpoint, bounding every request, and distinguishing route recovery from audible recovery.

## Evidence and confidence

Firsthand reports establish symptoms and reported interventions. They do not establish prevalence, a shared root cause, or causal effectiveness. Platform documentation establishes API contracts; AOSP establishes reference behavior, which Samsung can modify. Repository tests establish modeled behavior, not real Bluetooth sound.

| Evidence | Finding | Confidence and limit |
| --- | --- | --- |
| Samsung Members report, March 2025 [S1] | A52s media works while handsfree calls fail across earbuds and car systems | Firsthand symptom report; no controlled fault diagnosis |
| Samsung Community thread [S2] | Search-indexed April 2025 posts describe music working, calls failing, and temporary recovery after reboot | Supporting report only; full thread could not be retrieved during this review |
| A52s owner thread beginning April 2025 [S3] | Reports associate failure with `A528BXXSAGYA2`; both cellular and app calls are mentioned; fixes have inconsistent durability | Multiple anecdotes in one discussion, not independent measurements |
| UN1CA discussion February to July 2026 [S4] | Custom firmware has a similar failure; maintainer reports a possible missing build patch, offers a test build, then relays another user's successful result | Evidence for that custom-ROM incident; no demonstrated connection to the stock Samsung root cause |
| Local VW field report, 7 October 2026 [L1] | User reports uplink working and downlink silent on SM-A528B, Android 14, `A528BXXSBGYI3`; reboot reportedly restores sound | Important local reproduction report, but submitted logs end before the call |
| Android routing and capture contracts [S5–S9] | Control authority, endpoint changes, and limited audio observability constrain possible recovery | Strong API evidence; actual Samsung behavior needs validation |

### Timeline and device scope

The owner discussion [S3] begins on 21 April 2025 and names the January 2025 build. Some replies describe improvement after an April patch or safe-mode cycle, with later recurrence. Reports alone cannot date introduction of a single bug. A March 2025 Samsung Members report [S1] independently describes call-only failure. The local October 2026 report establishes continued symptoms on one particular September 2025 build, rather than failure on every build or every A52s.

Keep SM-A528B, SM-A528B/DS and SM-A528N results separate. A52 and A52 5G are different device families; S22 reports are useful comparisons, not A52s verification. Separate stock firmware from UN1CA and other ROMs. Track CSC/carrier configuration, security patch, call technology and accessory firmware when voluntarily available.

Samsung's current security scope [S10] does not list the A52s in its regular support categories. This is not proof that an exceptional update can never arrive. The project should work independently of a vendor fix without claiming Samsung has confirmed a permanent refusal to fix this issue.

## What is probably failing

Bluetooth music and Bluetooth telephony exercise different paths. Working media is compatible with a call-path failure; it does not demonstrate that the microphone, call transport, Telecom routing or telephony audio processing works.

For the stock A52s failure, the following remain hypotheses:

| Hypothesis | Supporting observation | Discriminating test |
| --- | --- | --- |
| Telecom route drift | Call remains on handset despite an eligible connected accessory | Observe selected endpoint before and after an endpoint request |
| HFP audio transport fails to establish or collapses | Bluetooth selection briefly appears, then falls back | Correlate selected endpoint with HFP audio events for that same device |
| Downlink or vendor audio state becomes invalid | User hears silence although remote party hears them | Controlled two-direction call test plus synchronized route and transport traces |
| Competing call or audio owner | Some owners associate changes with other apps | Reproduce with one variable changed, then restore it and repeat |
| Firmware integration regression | Similar symptoms across accessories and temporal update associations | Same phone/accessory with controlled firmware comparison, if practical |
| Accessory, carrier or IMS interaction | Failure may vary with head unit, Wi-Fi Calling or cellular mode | Change accessory or call technology independently |

Reboot resetting state is compatible with several hypotheses. It does not prove a cache problem, resource leak, Qualcomm HAL defect, or a particular Samsung service being at fault. The existing field report's assertion that uplink proves an SCO link is stronger than its logs support: car display/call control and a remote party hearing the user do not independently exclude a handset microphone path. Preserve the reported symptom; verify the physical paths.

## Failure taxonomy for the app

| Class | Observation | Automatic candidate | Verification boundary |
| --- | --- | --- | --- |
| Setup unavailable | No permission, call access, or actual service binding | None until initial access exists | Setup status must not say protected |
| Route drift | Intended endpoint exists, handset selected, no known override | Request intended endpoint once | Selected endpoint callback, then stable observation |
| Transport mismatch | Intended HFP endpoint selected, corresponding SCO audio disconnected | Bounded leave-and-return transaction | Same endpoint and transport reconnect; sound still unproven |
| Predicted route mismatch | Attribute routing prediction disagrees with Telecom | Corroboration and experimental policy only | Prediction is not measured cellular downlink |
| Suspected volume issue | Relevant volume evidence is anomalous | Optional restore to a prior user-approved level | Readback and user-volume precedence |
| Silent audio with normal metadata | User reports failure, available route and transport look normal | Validated preventive transaction, at most once | Only a controlled listening test verifies restoration |
| Endpoint absent | HFP connected but target not offered | Brief passive wait for reappearance | No general public API to reset the vendor stack |
| Ambiguous device or user choice | Multiple targets, switch to phone/wired/speaker | Yield | Never classify intentional privacy choices as failure |
| Unsupported call | Call is not exposed to this service | No intervention | No universal VoIP claim |

### Important API distinctions

`AudioManager.getAudioDevicesForAttributes()` predicts devices for audio attributes; it does not inspect the actual telephony downlink [S5]. Rename the app's `voiceOnBluetooth` concept accordingly. HFP audio state is transport evidence, not evidence that speech is audible. Unknown probe results must remain unknown.

`setCommunicationDevice()` accepts requests but gives audio-mode-owner requests priority [S5]. A true result is not a successful repair. `startBluetoothSco()` is not a reliable substitute during telephony. Avoid trying to seize audio mode to work around this constraint.

The current app uses legacy `InCallService.setAudioRoute()`. Android provides endpoint requests and endpoint callbacks from API 34; the API 37 `onCallEndpointRequested()` can also expose requests made through other in-call services [S6]. The A52s Android 14 path cannot rely on that newer callback.

Ordinary apps do not have general access to cellular call audio for silence detection; privileged capture requires special permission [S7]. Recording the microphone or running a voice recognizer would introduce privacy and audio interference without proving downlink delivery.

### Call access is the first feasibility gate

`CarLinkManager` asks for `DEVICE_PROFILE_WATCH` while associating a car. Android documents companion call access for wearable companions [S6], and companion profiles carry device and feature requirements [S8]. A car being accepted by an association dialog is insufficient evidence that this is a supported production enrollment mechanism.

Test on stock SM-A528B: association granted, app-op allowed, non-UI service actually bound, routes controllable, Samsung Phone still handles calls, then repeat after process death, normal reboot and app update. Record whether grants persist. Keep this setup method explicitly experimental until its suitability and behavior are established. An ADB app-op grant is a laboratory/developer enrollment alternative; it is not root and does not confer Bluetooth-stack restart rights.

A complete default dialer is another potential authorization path, but requires a real calling UI and emergency/fallback obligations. It is a separate product decision, not a small permission fix. Root, system installation or a persistent privileged bridge would change deployment and maintenance substantially. A bridge that must be restarted manually after reboot fails the intended unattended experience.

## Community workarounds and automation feasibility

| Reported action | Evidence | Could this ordinary app automate it reliably? |
| --- | --- | --- |
| Reboot or safe-mode cycle | Temporary improvement reported [S2, S3, L1] | No; also excluded by the product requirement |
| Clear Bluetooth Agent data/cache | Mixed reports, including recurrence [S3] | No supported permission to clear another system app's private data |
| Change SAP or A2DP hardware-offload options | Anecdotes, often combined, sometimes temporary [S3] | No supported production automation; media-option changes do not establish call-path causality |
| Reset network settings and re-pair | Anecdotal, disruptive, changes several variables | No; would erase user configuration and require setup |
| Uninstall a suspected app | Inconsistent results [S3] | No broad removal strategy; use only as a voluntary controlled experiment |
| Switch call away from Bluetooth and back | Existing app strategy; plausible Telecom recovery | Yes when access, endpoint availability and call state allow; efficacy is unproven for hidden silence |
| Toggle Bluetooth | Sometimes resets transient state | Restricted for apps targeting Android 13+, with specified management/system exceptions [S9]; also disrupts other devices |
| Restart Bluetooth process or audio HAL | Would affect deeper state | Not a supported action for an ordinary app |

A documented exception such as device-owner Bluetooth control is not permission to restart vendor audio services. Do not propose device-owner provisioning as a simple consumer setup step.

## Existing implementation audit

Paths are relative to the repository root. These are code observations at the baseline, not new runtime reproductions.

| Priority | File or component | Finding and consequence |
| --- | --- | --- |
| P0 | `setup/CarLinkManager.java`, `ProtectionStatus.java` | Watch-profile car association is assumed viable; ACTIVE depends on app-op and Bluetooth state, not demonstrated service routing capability |
| P0 | `core/repair/CallRepairEngine.java` | `advanceOperation()` runs before ordinary phase/classification checks. An in-flight rebuild needs explicit cancellation for held calls, extra calls and changed capabilities |
| P0 | Same engine | `MAX_ROUTE_ATTEMPTS` counts selected repair starts; preventive rebuild bypasses it, a rebuild has several commands, and return retries issue repeatedly after half-timeout. Three attempts is not three route operations |
| P0 | Same engine | `REBUILD_LEAVING` proceeds to return after timeout even without observed departure; route changes cannot be described as a proven teardown |
| P0 | Same engine | Eight-second grace and two-second command echo infer user intent from time. Manual handset choice in those windows can be mistaken for a failed app repair |
| P0 | Same engine | Faults disappearing or remaining unknown can produce HEALTHY/REPAIRED; a late fault that has not completed confirmation can be missed by final outcome |
| P1 | `telecom/CallAudioService.java` | Uses legacy route masks; no endpoint inventory, request completion/error, or device-specific target |
| P1 | `telecom/CallSession.java` | One engine spans all calls in a bound session. Call waiting and a second call need explicit global-route arbitration and separate call identity |
| P1 | `audio/HeadsetMonitor.java` | Any connected device's SCO may satisfy the selected device's health check. Proxy callbacks after close need a lifecycle guard |
| P1 | `audio/VoiceStream.java` | Predicted routing is called playback evidence; volume restore chooses about 60 percent without a prior user level |
| P1 | `core/report/CallHistory.java` | Risk history is global; one accessory's failures can trigger prevention for another |
| P1 | `telecom/CallSession.java` | Recreating a session recreates repair budgets; need conservative recovery from process death without repeated preventive bounces |
| P1 | `diagnostics/DiagnosticReport.java` | Export includes diagnostic log wholesale; a dedicated privacy filter and schema should enforce redaction |
| P2 | `update/UpdateInstaller.java`, README | Updates explicitly launch Android's installer; README's unattended self-update promise exceeds implemented behavior |
| P2 | README and research notes | Claims such as no battery use, proven prevention, guaranteed rebuild/codec negotiation and permanent lack of vendor fixes exceed available evidence |

The repository already has valuable foundations: pure Java core logic, modeled state-machine tests, Robolectric integration, lint, signed release infrastructure, bilingual UI, issue forms, contribution/security/support documents and a real-device test protocol. Extend these rather than replacing the project wholesale.

## Experiments that decide whether the goal is achievable

1. Prove service binding and routing authority using the proposed consumer enrollment and the ADB laboratory alternative separately. Outcome: supported, experimental or unavailable for each firmware/setup combination.
2. Reproduce the fault before intervention. Collect synchronized monotonic event times, endpoint selection, target HFP/SCO state, command results and independently observed uplink/downlink. Capture privileged dumps only in a consenting laboratory session.
3. Test a single directed Bluetooth request; if it fails, test one verified earpiece-and-return transaction. Count each platform request. Record command acceptance, endpoint departure/return and audible result separately.
4. If the fault is invisible to metadata but the transaction helps, compare prevention on and off across comparable calls and uptime. Introduce only that variable. No manual repair during a measured successful call.
5. If the endpoint is absent or the bounce leaves silence, record a failed recovery and stop ordinary-app escalation. That result constrains the product promise and motivates vendor/ROM collaboration.
